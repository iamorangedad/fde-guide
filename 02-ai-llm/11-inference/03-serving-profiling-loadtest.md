# 11.3 容量、剖析与可重复负载试验

> [🏠 返回主页](../../README.md) · [返回本章](README.md)

## 先修

[11.1](01-prefill-decode-kv.md) 的字节和延迟定义,[11.2](02-batching-quant-speculative.md) 的模拟器。第 8 章的 Nsight 和第 10 章的"一次只改一个因素"。

## 学习目标

- 用权重字节和 KV 预算估计还能缓存多少 token
- 把 GPU 小时和单价写成输入,避免虚构云报价
- 设计一次同时报告延迟、正确性和质量的负载试验
- 用两个假设情景练习"瓶颈 → 假设 → 还缺哪一次测量"

## 定义

**容量**在这里指:在声明的预留下,KV 预算还能放下多少 token。它不是 QPS。

$$
\mathrm{剩余} = \mathrm{GPU字节} - \mathrm{权重字节} - \mathrm{预留}
$$

$$
\mathrm{token上限} = \left\lfloor\mathrm{剩余} / \mathrm{每token字节}\right\rfloor
$$

预留包括分配器碎片、激活峰值、CUDA 上下文。预留是假设或测量,必须注明是哪一种。本章的例子把预留标成假设。

**费用**是 GPU 小时乘单价。单价使用调用方的货币单位。教程里的单价取 1,只为了让费用数值等于 GPU 小时,它不是任何云厂商的价格。

**负载试验**至少同时输出三类数:

1. 延迟:TTFT 和端到端的 p50、p95,算法写明
2. 正确性:完成的请求是否返回了预定结果,而不是只返回 200
3. 质量:在封存题目上的忠实度或精确匹配;延迟改善不能代替这一项

## 演算:一张假设的 24 GiB 卡

假设模型 \(P=7\times 10^9\),权重 bf16,每参数 2 字节:

$$
2P = 1.4\times 10^{10}\ \mathrm{字节} \approx 13.04\ \mathrm{GiB}
$$

卡容量 \(24\times 2^{30}\) 字节,预留假设 \(2\times 2^{30}\) 字节。剩余 \(9622320128\) 字节,约 8.96 GiB。沿用第 11.1 节每 token 131072 字节:

$$
\left\lfloor 9622320128 / 131072 \right\rfloor = 73412
$$

这是所有并发序列的 token 总和上限,不是"可以开 73412 路 长度 1 的请求"之外还有别的魔法。权重、预留或头数一变,整数就变。`capacity.py` 会在除法溢出时拒绝负数剩余,避免静默得到一个巨大的无符号数。

两张卡、运行 1800 秒、单价 1:GPU 小时是 \(2\times 1800/3600 = 1\),费用是 1。把单价换成合同里的数,费用才有货币意义。

## 假设情景,不是案例库里的实测

**情景 A。** 客服助手的提示经常到几千 token,解码不长。KV 公式说明字节随提示长度线性涨,权重不变。假设是:先限制最大提示、对重复前缀做缓存,而不是先量化权重。要补的测量是:真实提示长度的 p95、当前实现的每 token KV 字节、前缀命中率。没有这些数,就不能声称分页或前缀缓存"解决了"容量。

**情景 B。** 提示很短,并发解码很高。强度公式把解码放在带宽一侧。假设是:权重量化减少每步读取的权重字节,从而可能提高解码吞吐。要补的测量是:量化前后的任务忠实度、拒答率,以及同一负载下的 TTFT/TPOT p95。只报告显存下降是不完整的。本情景不给出任何加速倍数。

两个情景的共同点是:公式用来提出假设,测量用来接受或拒绝假设。把情景里的"可能"写成已经发生的百分比,就超出了材料。

## 剖析与试验怎么做

GPU 上的顺序和训练章相同,对象换成服务进程:

1. Nsight Systems 看预填内核、解码内核、调度空隙和主机同步
2. Nsight Compute 看解码内核更接近带宽顶还是算力顶,对照第 8 章
3. PyTorch Profiler 只在仍用 eager 的原型上有用;服务若已经是另一套运行时,以那套运行时的跟踪为准
4. 负载发生器固定随机种子、请求长度分布和并发。每次只改一个因素:块大小、最大批、是否量化
5. 同时记录错误率。超时要定义成失败还是计入 p95,两种选择都会改变数字,选定后不能中途更换

本仓库能重复运行的是 `loadsim`。它的"正确性"是回显 `expected` 字符串,精确匹配率在正常路径上为 1。这检验的是试验报告有没有把正确性列出来。它不生成语言,因此不能当作质量评测。质量评测仍然要用第 3 章和第 9 章的封存题目,在真实服务上跑。

编写环境没有 GPU,也没有安装 vLLM 或 Nsight。上面的工具步骤是文档要求的工作顺序,不是已经执行的实验。

## 排障

| 现象 | 读法 |
|---|---|
| 公式说还能放 7 万 token,运行时 1 万就 OOM | 预留假设太小,或实现按最大长度连续预留。用分配峰值替换假设预留 |
| p50 很好、用户仍抱怨 | 看 p95 和队列。SLO 没写分位数时,先补定义再优化 |
| 压测 QPS 很高,抽查答案张冠李戴 | 正确性门没开。吞吐只统计了 HTTP 200 |
| 量化试验和组批试验同一天改的 | 无法归因。拆开,各带一份数据哈希和配置 |
| 报告引用了本章的 73412 | 那是假设结构和假设预留下的除法,不是容量测试结果 |

## 练习

1. 权重改成每参数 1 字节(假设的压缩存储),其他数不变:\(P=7\times 10^9\),24 GiB 卡,2 GiB 预留,每 token 131072 字节。剩余字节和 token 上限各是多少?
2. 设计一次负载试验的最小记录表,至少 8 个字段。哪些字段缺失时,延迟数字不能被别人复现?
3. 情景 A 和情景 B 的第一假设为什么不应该相同?

### 参考解答

1. 权重 \(7\times 10^9\) 字节。剩余 \(24\times 2^{30} - 7\times 10^9 - 2\times 2^{30} = 16622320128\) 字节。token 上限是 \(\lfloor 16622320128 / 131072\rfloor = 126818\)。这仍然是除法,压缩存储是否真的每参数 1 字节要看格式和尺度元数据,第 9 章已经要求把元数据加回去。
2. 至少包括:服务版本、模型与适配器哈希、GPU 型号、并发、输入长度分布及种子、输出长度上限、成功定义、分位数算法、墙钟起点(是否含排队)、质量集合标识、错误率、配置差异(相对上一次只改了什么)。缺 GPU、版本、种子或成功定义时,延迟数字不能复现。
3. 情景 A 的字节随序列长度涨,第一项是 KV。情景 B 的每步要反复读权重,第一项是权重带宽。用量化权重去处理一个 KV 已经占满的长上下文,或者用缩短提示去处理一个短解码带宽问题,都改错了行。

## 小结

容量是剩余字节除以每 token 字节。费用是 GPU 小时乘你自己的单价。负载试验同时交延迟、正确性和质量。假设情景只负责把公式翻译成下一步要测什么,不负责提供加速比。
