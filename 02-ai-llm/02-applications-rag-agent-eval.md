# 3.2 应用系统：RAG、Agent 与评测

> [🏠 返回主页](../README.md) · [返回本章入口](README.md) · [上一节 3.1](01-business-and-model-choice.md) · [下一节 3.3](03-pretraining-and-adaptation.md)

## 先修

[3.1](01-business-and-model-choice.md) 的约束表与方法阶梯。

## 学习目标

- 画出带权限过滤的 RAG 管线，并能区分「检索失败」与「生成失败」
- 在 Agent 与固定工作流之间做可辩护选择，并为工具调用设置成本与风险上限
- 建立分层评测：单元断言、抽样人工、必要时校准的模型评判

## 定义

**上下文窗口**：单次请求可送入模型的 token 上限。它限制「一次塞进多少检索片段」，不消除对外部知识库的需求。

**RAG（检索增强生成）**：先从外部语料检索相关片段，再条件生成答案，以便提高事实性与可溯源。

**嵌入（embedding）**：把文本映到向量空间，使语义相近者距离更近；常与关键词检索（如 BM25）组成**混合检索**。

**工具调用**：模型输出结构化调用意图，由运行时执行并返回结果；模型本身不直接拥有数据库写权限。

**Agent**：由模型动态决定下一步与工具；**工作流**：步骤由代码预先固定。工程上应优先最简单仍能完成任务的方案。

**评测（eval）**：针对任务定义的、可重复执行的质量测量，用来决定改提示、改检索还是改训练。

## 原理：RAG 管线与诊断

```text
文档 → 解析/清洗 → 切分 → 嵌入 → 索引
用户问题 →（查询改写）→ 检索 top-k →（重排）→ 组装上下文 → 生成 + 引用
                              ↑
                     元数据/ACL 过滤必须在此发生
```

| 决策 | 选项 | 取舍 |
|---|---|---|
| 切分 | 固定长度 / 按标题段落 | 结构切分常更利于条款、手册 |
| 检索 | 向量 / 词法 / 混合 | 编号、型号、专有名词更吃词法信号 |
| 重排 | 交叉编码器等 | 精度↑、延迟↑ |
| 权限 | 检索前过滤 vs 生成后检查 | **必须检索时过滤**；生成后过滤无法防止上下文泄露给模型 |

**诊断顺序**：先人工看失败样本——是 top-k 里根本没有金段落（召回问题），还是金段落在但答案胡编（生成/提示/忠实度问题）。两类问题的修复完全不同；混在一起只会「换更大模型」。

### Agent 与工作流

常见模式：提示链、路由、并行、编排者-执行者、评估者-优化者。企业落地四条硬约束：

1. 工具 schema 严格、服务端再校验；
2. 最大步数与费用上限；
3. 写库、付款、对外发送等需人工确认或独立策略引擎；
4. 全链路 trace（提示版本、检索命中、工具出入参）。

结构化抽取示例（教学用，依赖你自己的运行环境）：

```python
from pydantic import BaseModel, ValidationError

class Invoice(BaseModel):
    vendor: str
    total: float
    currency: str

def extract(text, llm, max_tries=3):
    for _ in range(max_tries):
        raw = llm(f"从发票抽取 JSON，字段 vendor,total,currency:\n{text}")
        try:
            return Invoice.model_validate_json(raw)
        except ValidationError as e:
            text = text + f"\n上次输出不合法: {e}"
    raise ValueError("抽取失败，转人工")
```

### 评测三层

1. **单元级断言**：JSON 可解析、必含字段、禁止短语、引用 id 存在——代码判定。
2. **模型评判（LLM-as-judge）**：必须与人工抽样对齐并定期校准；不能当作无偏真值。
3. **人工与线上**：采纳率、修改率、任务完成时间、升级人工比例。

RAG 常用拆分指标：检索 Recall@k、答案忠实度（是否被引用支持）、答案相关性。先做几十到上百条真实轨迹的**错误分析**，再针对高频桶建集，而不是先买「自动评测平台」。

## 生产化关注点

- **延迟与成本**：缓存重复查询、小模型路由简单意图、流式输出改善体感。
- **安全**：提示注入（含检索片段与工具返回中的间接注入）、越权、输出过滤。
- **版本**：提示、模型、索引、切分规则都要可追溯；回滚要整条链路一起回。

## 案例（虚构）

法务合同问答不准。错误分析：条款编号「第 7.2 条」纯向量检索常失配；多版本合同未按版本元数据过滤。改为混合检索 + 版本过滤后，引用命中率上升（具体百分比需在你的集上重测，此处不编造）。**教训**：先看数据，再改架构。

## 练习

1. 为内部知识库设计 RAG，说明权限如何贯穿检索；为什么「生成后再检查是否越权」不够。
2. 收集（或合成）30 条问答，做错误归类表：检索 / 切分 / 权限 / 提示 / 幻觉 / 工具。
3. 发票字段抽取 vs 开放式竞品调研：哪个用工作流，哪个才考虑 Agent？为什么？

### 参考解答

1. 索引或检索查询必须带用户可访问的 doc id / 部门标签；过滤在取 top-k 之前。生成后再查无法阻止敏感片段进入上下文窗口。
2. 归类表应能直接映射到下一周的工程任务（改切分、加 BM25、修 ACL……）。
3. 发票字段步骤可预知 → 工作流 + 校验；开放式调研路径分叉多 → 才考虑受限 Agent，仍要步数与工具白名单。

## 小结

LLM 应用系统 = 数据 + 检索 + 模型 + 工具 + 评测。评测是方向盘；权限是检索问题，不是提示词问题。
