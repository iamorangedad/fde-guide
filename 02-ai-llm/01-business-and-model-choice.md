## 学习目标

- 把客户口述的「要一个 AI」拆成可验证的任务、数据边界与失败代价
- 用延迟、成本、隐私、可控性四类约束做第一轮选型
- 在「提示 / RAG / 微调 / 对齐 / 自建预训练」之间给出可辩护的默认顺序，而不是默认训练

## 定义

**前线部署工程师（FDE）语境下的语言模型项目**，通常不是从零训练基座，而是在客户环境里把模型能力接进现有系统：身份与权限、知识源、工具、审计与评测。成功标准几乎总是业务指标（工单解决率、合同条款定位准确率、人工修改率），而不是公开榜单分数。

**模型选型**指在给定约束下选择：调用哪家 API、部署哪个开源权重、是否需要私有化、是否需要改权重。选型发生在写训练脚本之前。

**失败代价**指答错一次的业务后果。客服话术写错可能可接受；医疗剂量、付款指令、权限判断写错通常不可接受——后者必须用程序门禁与人工确认，不能指望「模型学会谨慎」。

## 原理：先写约束，再写架构

把需求写成四张表，任何一项空白都不要进入「我们微调一下」：

| 维度 | 要写清的问题 | 典型答案形态 |
|---|---|---|
| 任务 | 输入是什么、输出必须含什么字段、什么算成功 | 「根据用户工单与知识库，返回可执行步骤 + 引用」 |
| 数据 | 知识是否会变、谁有权看、能否出境 | 「制度月更；按部门 ACL；不可出内网」 |
| 系统 | 现有身份源、工单系统、审计要求 | 「OIDC + ServiceNow；全链路留痕」 |
| 运行 | p95 延迟、并发、预算、可用性 | 「首 token < 2s；峰值 20 QPS；月预算上限」 |

### 默认方法阶梯（业务视角）

从便宜、可逆到昂贵、难回滚：

1. **提示与校验器**：格式、枚举字段、JSON schema、拒答策略。失败可立刻改提示。
2. **RAG / 工具调用**：事实在外部系统；权限在检索或 API 层强制。细节见 [3.2](02-applications-rag-agent-eval.md)。
3. **监督微调（SFT）**：行为（格式、语气、工具参数形状）在提示下仍不稳，且有干净输入输出对。概念见 [3.4](04-finetuning-and-alignment.md)。
4. **偏好对齐（DPO / RLHF 等）**：需要在「同样正确」的多种答法中偏好某类风格或安全策略，且有成对或成组偏好数据。
5. **继续预训练 / 自建预训练**：语料分布与通用基座差得很大，且有大规模领域文本与算力——FDE 项目里最少见，见 [3.3](03-pretraining-and-adaptation.md)。

**把会变的制度写进权重**通常是错误默认：制度下周改版时，你要的是索引与权限更新，不是一次昂贵的再训练。把「背事实」和「学行为」分开，是本章反复出现的原则。

### API、开源权重与私有化

| 选项 | 适合 | 主要代价 |
|---|---|---|
| 托管 API | 快速验证、流量中等、数据可按合同处理 | 供应商依赖、出站延迟、合规审查 |
| 自托管开源权重 | 数据不出域、要改服务形态或适配器 | 运维、GPU 容量、安全基线自负 |
| 微调后的适配器 + 共享基座 | 多租户/多任务、基座统一升级 | 合并与未合并部署形态要设计清楚 |
| 从头预训练 | 几乎只有平台级组织 | 数据工程与集群，超出多数 FDE 交付范围 |

选型时问三个「能不能」：**能不能把原文引用交给用户审计？能不能按身份过滤知识？能不能在模型之外拒绝高风险动作？** 三个都能否定，再谈更大模型或更多训练。

## 演算与案例（虚构）

**情景 A（合成）**：某制造企业要「设备手册问答」。手册 PDF 每月更新；产线工人与工程师看到的章节不同；答案必须带章节号。

- 正确默认：解析 + 按角色元数据过滤的混合检索 + 生成带引用；评测看「引用是否支持答案」。
- 错误默认：把整本手册做 SFT「背下来」。手册一改，权重过期，且无法按角色隔离。

**情景 B（合成）**：客服系统要稳定输出「工单字段 JSON」，提示加校验仍有 15% 缺字段（该比例是本题假设输入，不是行业统计）。

- 可考虑：少量「对话 → 合法 JSON」的 SFT 或强约束解码；事实字段仍来自 CRM 工具调用，不靠模型编造订单号。

**容量直觉（闭式，假设输入）**：若 SLA 要求 p95 端到端 3s，其中检索 200ms、业务系统 300ms，则模型生成预算约 2.5s。若平均输出 400 token、解码约 40 token/s（假设），单请求解码约 10s——不满足。结论不是「换更大模型」，而是减输出、流式交互、或换更快的小模型/推理栈。具体 KV 与批调度见 [3.7](07-training-and-inference-systems.md)。

## 练习

1. 客户说「我们要 ChatGPT，但数据不能出公司」。写出至少四个必须补问的问题，并说明每个问题如何改变选型。
2. 将下列需求标成「提示 / RAG / SFT / 对齐 / 预训练」中的首选（可多选但需排序）：(a) 回答必须引用当前有效的安全规程；(b) 拒答医疗剂量建议；(c) 始终用公司敬语模板收尾；(d) 读懂内部电路图扫描件里的稀有符号（假设通用模型几乎未见过）。
3. 为什么「先上最大模型再优化」在 FDE 交付里常常是坏策略？

### 参考解答

1. 示例：数据分类与出境规则；身份源与 ACL；是否必须离线； humant-in-the-loop 场景；延迟与并发；现有知识库形态；审计字段。任一答案变化都可能从 API 转向自托管，或从「可训练」转为「只检索」。
2. (a) RAG（事实变更 + 引用）；(b) 系统策略/分类器/拒答规则，必要时偏好数据对齐，但硬拒答应在程序层；(c) 提示或少量 SFT；(d) 可能需要领域数据的继续预训练或专用视觉文档管线——先确认问题是否真是「符号未见过」，还是解析质量差。
3. 更大模型放大单位成本与延迟，掩盖检索/权限/评测缺陷；上线后难以归因。应先用可观测的管线证明瓶颈在模型能力，再放大模型。

## 小结

FDE 的第一章不是 CUDA，而是把业务写成约束与可测任务。方法阶梯从提示与 RAG 往上走；训练是对「稳定行为」或「分布偏移」的处方，不是身份象征。
